## How WireGuard Works (Simply)

WireGuard creates an encrypted tunnel between two peers using public/private key cryptography. Unlike OpenVPN or IPsec, there is no handshake protocol, no certificates, no connection state — it's just UDP packets, encrypted with the peer's public key, sent to a known IP and port.

```
Your laptop                        WireGuard server
──────────                         ────────────────
wg0 / oci / vpn                    wg0
10.8.0.2                           10.8.0.1

  [ encrypted UDP ] ──────────▶  port 51820
  [ encrypted UDP ] ◀──────────
```

**Key concepts:**
- **Interface**: A virtual network interface (`wg0`) with its own IP address on both ends.
- **Peer**: Each side knows the other's public key and (optionally) endpoint IP:port.
- **AllowedIPs**: The list of IP ranges whose traffic is sent into / accepted from the tunnel. This acts as both a routing rule and an access control list simultaneously.
- **Handshake**: Happens automatically when you send traffic. The server never "calls back" — the client initiates. After a successful handshake, both sides can send.
- **PersistentKeepalive**: Sends a keepalive packet every N seconds. Needed when the client is behind NAT, so the NAT mapping doesn't expire and the server can still reach the client.

That's it. There's no daemon managing connections. WireGuard is in the Linux kernel. `wg-quick` is just a shell script wrapper that sets up the interface, routes, and firewall rules described in the config file.

## What Needs to Be in Place

Getting WireGuard working end-to-end requires rules at **four layers**. All four must be correct simultaneously — failure at any one layer causes 0 bytes received with no obvious error message.

### Layer 1: Cloud Security Rules (OCI Security Lists / NSGs)

This is the **outermost gate** — traffic that doesn't pass here never reaches the VM.

OCI has two independent security layers that are both enforced:
- **Security Lists**: attached to subnets, stateful
- **Network Security Groups (NSGs)**: attached to VNICs, stateful

Both must allow UDP 51820 inbound to the WireGuard server's subnet/VNIC.

**In Terraform (`modules/network/vcn.tf`):**
```hcl
ingress_security_rules {
  protocol  = "17"   # UDP
  source    = "0.0.0.0/0"
  stateless = false

  udp_options {
    min = 51820
    max = 51820
  }
}
```

> **Why `0.0.0.0/0`?** WireGuard's cryptographic authentication means only clients with the correct private key can use the tunnel. Restricting by source IP only adds friction — clients on dynamic IPs will break. Let WireGuard handle auth.

**In Terraform (`modules/network/wireguard_nsg.tf`):**
```hcl
resource "oci_core_network_security_group_security_rule" "wireguard_ingress_udp" {
  direction                 = "INGRESS"
  network_security_group_id = oci_core_network_security_group.wireguard.id
  protocol                  = "17"
  source                    = "0.0.0.0/0"
  source_type               = "CIDR_BLOCK"
  stateless                 = false

  udp_options {
    destination_port_range {
      min = 51820
      max = 51820
    }
  }
}
```

### Layer 2: Host Firewall (iptables on the WireGuard Server)

OCI Ubuntu images ship with iptables rules that end with a blanket `REJECT` rule:

```
-A INPUT -j REJECT --reject-with icmp-host-prohibited
-A FORWARD -j REJECT --reject-with icmp-host-prohibited
```

This means **even if OCI's security layers allow the traffic in, the OS will reject it**.

Three things must be opened:

| Chain | Purpose |
|-------|---------|
| `INPUT -p udp --dport 51820` | Allow WireGuard handshake packets to reach the `wg0` interface |
| `FORWARD -i wg0` | Allow packets arriving from VPN clients to be forwarded |
| `FORWARD -o wg0` | Allow reply packets to be forwarded back to VPN clients |

Plus NAT so that traffic from VPN clients appears to come from the server's own IP when it reaches the private subnet:

```
POSTROUTING -t nat -o ens3 -j MASQUERADE
```

**Where to put these rules:** In the WireGuard config's `PostUp`/`PreDown`, so they're applied when the interface comes up and cleaned up when it goes down.

**In `wg0.conf` (generated by `wireguard-install.sh`):**
```ini
[Interface]
Address    = 10.8.0.1/24
PrivateKey = <server_private_key>
ListenPort = 51820
PostUp     = iptables -I INPUT 1 -p udp --dport 51820 -j ACCEPT
PostUp     = iptables -I FORWARD 1 -i wg0 -j ACCEPT
PostUp     = iptables -I FORWARD 1 -o wg0 -j ACCEPT
PostUp     = iptables -t nat -I POSTROUTING -o ens3 -j MASQUERADE
PreDown    = iptables -D INPUT -p udp --dport 51820 -j ACCEPT
PreDown    = iptables -D FORWARD -i wg0 -j ACCEPT
PreDown    = iptables -D FORWARD -o wg0 -j ACCEPT
PreDown    = iptables -t nat -D POSTROUTING -o ens3 -j MASQUERADE
```

> **Discovery — primary interface name:** Don't hardcode `ens3`. The interface name varies by instance shape and OS. Detect it dynamically *before* writing the config:
> ```bash
> PRIMARY_IFACE=$(ip -4 route show default | awk '{print $5}' | head -n1)
> ```
> Then use `$PRIMARY_IFACE` when writing `wg0.conf`. This runs in bash during cloud-init, before the heredoc writes the file — so the value is interpolated correctly.

> **Pitfall — `SaveConfig = true`:** If you add `SaveConfig = true` to `[Interface]`, WireGuard will write its in-memory state back to `wg0.conf` on shutdown. On a freshly started interface with no active peers, this **erases all `[Peer]` sections** from the file. Do not use `SaveConfig = true`.

### Layer 3: Kernel IP Forwarding

The Linux kernel must be configured to forward packets between interfaces. Without this, packets arriving on `wg0` destined for `10.0.0.x` are silently dropped.

**In `wireguard-install.sh`:**
```bash
echo "net.ipv4.ip_forward=1" >> /etc/sysctl.conf
sysctl -p
```

### Layer 4: Routes

Routing must be correct on **both** the client and the server.

#### Server-side: nothing extra needed for split tunnel
The server's `wg0` interface is `10.8.0.1/24`. It knows that `10.8.0.0/24` is reachable via `wg0`. The MASQUERADE rule handles making traffic look like it comes from the server when it enters the VCN. OCI's VCN routing handles the rest.

#### Client-side: split tunnel (`oci` config)
`AllowedIPs = 10.8.0.0/24, 10.0.0.0/16` — wg-quick adds these as routes pointing at the tunnel interface. Simple. The default route stays on your real interface.

```
10.0.0.0/16 dev oci scope link
10.8.0.0/24 dev oci proto kernel scope link src 10.8.0.2
```

#### Client-side: full tunnel (`vpn` config) — the tricky part
`AllowedIPs = 0.0.0.0/0` means "route everything through the tunnel." But this creates a bootstrapping problem: if you route everything through the tunnel, how do you reach the WireGuard server to maintain the tunnel?

`wg-quick` solves this with **policy routing**:
1. Mark all WireGuard-generated packets with fwmark `51820`
2. Add a rule: packets with that mark use the normal routing table
3. Add a rule: all other packets use routing table `51820` (which has `0.0.0.0/0 dev vpn`)

```
ip -4 rule add not fwmark 51820 table 51820
ip -4 rule add table main suppress_prefixlength 0
ip -4 route add 0.0.0.0/0 dev vpn table 51820
```

This is automatic when `AllowedIPs = 0.0.0.0/0` — wg-quick detects it and switches to this mode. **You don't need to add these rules manually.**

However, there is still a routing loop problem on some systems (notably openSUSE). The `suppress_prefixlength 0` rule suppresses default routes from the main table — but on some kernels/distros the endpoint host route is not pre-populated. Fix: add a specific host route to the WireGuard server's public IP via your real default gateway **before** the tunnel takes over all traffic.

**In the client config `PostUp`:**
```ini
PostUp   = ip route add 144.21.35.212/32 via $(ip -4 route show default | awk '{print $3}' | head -1) dev $(ip -4 route show default | awk '{print $5}' | head -1) 2>/dev/null || true
PreDown  = ip route del 144.21.35.212/32 2>/dev/null || true
```

> **Pitfall — shell variables in WireGuard configs:** WireGuard config files do not support shell variable expansion. However, `PostUp`/`PreDown` values are passed to `/bin/sh -c`, so **command substitution** (`$(...)`) works fine. Plain `$VAR` references do not — there is no environment to expand them from. Use subshells.

> **Pitfall — Terraform templatefile and `$` signs:** If you generate WireGuard configs using Terraform's `templatefile()`, any `$` in `PostUp`/`PreDown` that isn't a Terraform variable reference must be escaped as `$$`. For example:
> ```hcl
> PostUp = ip route add ${public_ip}/32 via $$(ip -4 route show default | awk '{print $$3}' | head -1) ...
> ```
> Inside a cloud-init YAML, this same content may need further escaping depending on how it's embedded (heredoc vs quoted string).

## Our Configuration Problems

### Problem 1: Missing INPUT iptables rule ⭐ (root cause of 0B received)

**Symptom:** `wg show` on the client shows `transfer: 0 B received, 148 B sent`. The handshake never completes. No errors anywhere.

**Why it happens:** OCI Ubuntu images have this at the end of the INPUT chain:
```
-A INPUT -j REJECT --reject-with icmp-host-prohibited
```
UDP 51820 packets arrive at the VM, pass OCI's security layers, but are immediately rejected by the OS before WireGuard's kernel module can process them.

**Why it's non-obvious:**
- OCI's security list and NSG show UDP 51820 as allowed — you assume the firewall is done.
- `wg show` on the server shows the peer is configured but gives no indication that packets are being rejected before they arrive.
- There's no connection refused error — ICMP host-prohibited is silently dropped by most clients.
- The FORWARD chain issue (below) is more commonly documented, so you fix that first and still see 0 bytes.
- `ss -ulnp` shows wg0 listening on 51820 — looks fine.
- Nothing in `/var/log/syslog` unless you specifically add iptables LOG rules.

**Fix:** Add the INPUT rule to `PostUp` in `wg0.conf`:
```ini
PostUp  = iptables -I INPUT 1 -p udp --dport 51820 -j ACCEPT
PreDown = iptables -D INPUT -p udp --dport 51820 -j ACCEPT
```

### Problem 2: Missing FORWARD iptables rules (VPN traffic not forwarded)

**Symptom:** Handshake succeeds (bytes received), but traffic to private subnet hosts returns nothing.

**Why it happens:** Same OCI blanket `REJECT` — this time on the FORWARD chain. Packets from the VPN client (`10.8.0.2`) destined for `10.0.0.x` arrive on `wg0` and are immediately rejected before being forwarded to `ens3`.

**Additional complication:** UFW (if installed) inserts its own chains (`ufw-before-forward` etc.) but they sit *after* the OCI REJECT rule in the chain ordering. Allowing forwarding in UFW does nothing if the REJECT fires first.

**Fix:** Insert at position 1 (before the REJECT):
```ini
PostUp = iptables -I FORWARD 1 -i wg0 -j ACCEPT
PostUp = iptables -I FORWARD 1 -o wg0 -j ACCEPT
```

### Problem 3: Hardcoded network interface name

**Symptom:** MASQUERADE rule fails silently; NAT doesn't work; traffic can enter the tunnel but can't reach private hosts.

**Why it happens:** The install script was written with `enp1s0` hardcoded (typical for KVM VMs). OCI AMD instances use `ens3`. ARM instances may use yet another name. The MASQUERADE rule references a non-existent interface and the NAT table entry is never created.

**Fix:** Detect dynamically before writing the config:
```bash
PRIMARY_IFACE=$(ip -4 route show default | awk '{print $5}' | head -n1)
```

### Problem 4: `systemctl reload ssh` killing the install script

**Symptom:** Wireguard instance boots, cloud-init runs, but `wg0` never starts. Checking the instance shows all steps up to the SSH config change completed, then nothing.

**Why it happens:** The install script sets `set -euo pipefail`. During cloud-init, `sshd` is socket-activated — it's not "active" yet, so `systemctl reload ssh` returns a non-zero exit code. `set -e` immediately kills the script. Every line after that — including `systemctl enable --now wg-quick@wg0` — never runs.

**Why it's non-obvious:** The cloud-init log shows the script started. There's no error message — the script just stops. `wg0` is absent from `ip link show`. You might assume the install script didn't run at all.

**Fix:**
```bash
systemctl reload ssh 2>/dev/null || true
```

### Problem 5: `SaveConfig = true` eating peer configs

**Symptom:** After restarting `wg-quick@wg0`, all `[Peer]` sections vanish from `wg0.conf`. Clients can no longer connect. Regenerating the config restores it — until the next restart.

**Why it happens:** `SaveConfig = true` tells WireGuard to write its in-memory runtime state back to the config file when the interface goes down. On a server that just started with no active client connections, the runtime state has `[Interface]` only. This overwrites the file, deleting all peers.

**Fix:** Remove `SaveConfig = true` entirely. Manage peers statically in the config file.

### Problem 6: ssh_config.sh using public IPs for -via-wg SSH entries

**Symptom:** `ssh k3s1-via-wg` connects initially (ProxyJump through wireguard), then hangs or fails to reach the k3s node.

**Why it happens:** The `ssh_config.sh` script used the k3s nodes' public IPs for the `HostName` in `-via-wg` entries. When jumping via Wireguard, the ProxyJump host (the Wireguard server) tries to open a connection to the public IP of the k3s node. But the k3s nodes are in a private subnet — they have no outbound internet route to bounce back through. Private subnet → public IP → NAT → same private subnet is not a path that OCI routes.

**Fix:** Use private IPs for all `-via-wg` entries. The Wireguard server is in the VCN and can reach private IPs directly.

## Common Pitfalls with AllowedIPs = 0.0.0.0/0

### 1. You lose internet access immediately if the tunnel drops
Unlike split tunnel, all traffic goes through the VPN. If the WireGuard process crashes or the server goes down, you have no internet. Keep the `oci` (split tunnel) config as a fallback.

### 2. DNS leaks
Even with `DNS = 1.1.1.1` in the config, some systems may continue using the local resolver for a window of time, or leak DNS queries through the physical interface. Use `resolvectl status vpn` to verify DNS is being served through the tunnel interface.

### 3. Routing loops on clients that don't auto-add the endpoint host route
`wg-quick` on most modern Linux distros automatically adds a `/32` host route for the WireGuard server's public IP via your real gateway before installing the `0.0.0.0/0` policy rule. Some distros (notably openSUSE Tumbleweed) do not. Without this, traffic to `144.21.35.212` also goes into the tunnel → tunnel tries to reach `144.21.35.212` → loop → tunnel drops.

**Fix:** Add it explicitly in `PostUp` (as we do):
```ini
PostUp  = ip route add <server_public_ip>/32 via $(ip -4 route show default | awk '{print $3}' | head -1) dev $(ip -4 route show default | awk '{print $5}' | head -1) 2>/dev/null || true
PreDown = ip route del <server_public_ip>/32 2>/dev/null || true
```

### 4. Two clients with the same private IP / same key
If you bring up both the `oci` (split tunnel) and `vpn` (full tunnel) configs at the same time, both will try to use `10.8.0.2` and the same keypair. The server will see conflicting peers. Bring only one up at a time.

### 5. PersistentKeepalive is required when behind NAT with full tunnel
Without it, the NAT mapping on your router expires (typically 30-300 seconds for UDP). The server can no longer reach you. With full tunnel, all your traffic is WireGuard — if the server can't reach you, nothing works. `PersistentKeepalive = 25` keeps the NAT mapping alive.

### 6. MTU mismatches causing large packets to silently fail
WireGuard adds ~60 bytes of overhead per packet. If your physical MTU is 1500, WireGuard's MTU should be ~1420. `wg-quick` sets this automatically, but if you're on a link with a non-standard MTU (e.g., PPPoE at 1492), you may need to set it explicitly:
```ini
[Interface]
MTU = 1380
```
Symptom: small requests work (ping, DNS), large transfers hang or fail (HTTPS, SSH file transfers).

### 7. Full tunnel breaks SSH to the WireGuard server itself
Once full tunnel is up, SSH to the server's public IP goes through the tunnel. If the server is the WireGuard endpoint, this works — but if the tunnel drops, you can't SSH in to fix it. Use the private IP via the OCI console or keep a separate out-of-band access method.
